# AI Software Workshop (blueprint)

A battle-tested **way of working for building software with LLM agents** -
roles, skills, handoffs, gates and registers, distilled from a real project
(phases 01-08 of a V-model build, an MVP release gate, and months of
incremental operation). Everything here describes what actually worked and
what actually went wrong - not theory.

The core problem this solves: agents are fast but unreliable partners.
They duplicate edits, claim things that are not on disk, loop forever on
impossible verification criteria, and burn budget politely. This workshop
is the set of guardrails that makes them productive anyway - with the
human keeping exactly the decisions that matter.

## What's inside

```
workshop/
  setup.ps1                        bootstrap: creates the whole workspace skeleton (idempotent)
  agent-roles.md                   the roles, the two rules, evidence rule, model routing
  handoff-template.md              the work-unit contract (incl. MANDATORY abort conditions)
  handoff-coordinator.md           the steering chat: how units are planned, dispatched, closed
  handoff-methods.md               the methods chat: who maintains the way of working itself
  agent-navigation-concept.md      token-efficient navigation for big registers (STATE -> INDEX -> grep)
  agent-navigation-supplement.md
  skills/                          13 method playbooks (see its README for the index)
  _template-software-project/      V-model project skeleton (phases 01-08 + registers)
  _template-knowledge-project/     writing-project skeleton (phase-based)
```

## The five load-bearing ideas

1. **Roles, not chats.** Owner (decides), Author/File-Holder, Reviewer,
   Researcher, Registrar, Coordinator (steers), Product Manager (product
   view). Two iron rules: **one editor per file at a time** and
   **reviewer != author**. Roles are assigned per task, in the handoff.
2. **The dated handoff is the binding specification.** Nothing is
   specified only in chat. Every unit carries a done criterion AND -
   since a sub-agent once burned a whole token budget in an overnight
   retry loop - a mandatory **abort condition**: after a bounded number
   of targeted attempts, STOP and report the gap. A gap reported inside
   the abort budget is a completed unit with a finding, not a failure.
3. **The evidence rule.** Status claims only with verifiable evidence -
   a file, a CI run, command output. "Not verifiable" is a legitimate
   answer. Reviewers check claims **against files, not against the
   report**.
4. **Registers + a relation graph as the project's nervous system.**
   Requirements (REQ), decisions (DEC), changes (CHG), open questions
   (OQ), risks, interfaces (IF), submodules (SUB), test cases (TC) -
   machine-readable, regenerated by a script, queryable as a graph
   (`tools/build_index.py` -> INDEX/TRACEABILITY/graph.json,
   `tools/query_graph.py` for questions, `graph.bat` for the HTML
   viewer). Ships in the project template from day 1 - nothing to
   retrofit when the registers grow. This is what survives window
   switches and keeps months of incremental work traceable.
5. **Model routing by cost class.** Not every unit deserves the strong
   model. Builds with a mechanical done criterion run on the cheap
   class; reviews/research on a second external model; the expensive
   top model only for truly critical judgements. Agents cannot switch
   models - the handoff names the class, the human sets it when opening
   the window.

## Quickstart

Full documentation: [docs/architecture.md](docs/architecture.md) (the
moving parts and WHY they exist) and [docs/way-of-working.md]
(docs/way-of-working.md) (the operating guide: starting, daily rhythm,
incremental mode, window hygiene).

```powershell
git clone <this repo> my-workspace
cd my-workspace
powershell -ExecutionPolicy Bypass -File .\workshop\setup.ps1
```

The script (idempotent, safe to re-run) creates the full skeleton around
itself: `apps/`, `knowledge/`, the project templates, the root README,
and thin skill pointers for Claude Code (`.claude/skills/`).

**Start your first project** (software):

1. Copy `workshop/_template-software-project/` to `apps/<name>/`.
2. Fill in `CLAUDE.md` and `README.md` (one short session).
3. `cd apps/<name>; git init; commit; push` to its own repo.
4. Open a steering chat: point it at `workshop/handoff-coordinator.md`.
5. Phase 01 with `workshop/skills/testable-requirements/` ->
   `requirements.md` -> review gate. Then phases 02-08, each with its
   skill and a gate. Not every project needs all phases in full depth -
   but phase 01 and the register discipline from day 1 are not
   negotiable.

## How it was built (provenance)

Every skill in `skills/` was distilled **after** its phase had been
lived, on owner request - never from theory. The playbooks carry their
origin stories with them (what failed, what it cost, what the fix was).
Expect them to read like field reports, because they are.
