# Skill: cross-document consistency sweep

Finding the defects that live *between* documents rather than inside them. Distilled from two
cross-checks of the geo-knowledge-guide solution concept (2026-08-07).

**Use when:** reviewing a spec-driven repo before a gate; after incorporating review findings;
after any change that touches several control files; whenever two agents have worked the same
material.

---

## Why this exists

In both cross-check rounds of a carefully written concept, **every serious finding was a seam
between documents, not a flaw in the thinking.** The requirements were sound, the decisions
were sound, the concept was sound - and the coverage table, the traceability matrix and the
release plan disagreed with each other and with the requirements file.

That is the normal failure mode of this way of working, and it is invisible when you read each
document on its own. It is only visible when you compare them mechanically.

## The method

1. **Extract mechanically, never by eye.** Pull IDs, priorities and statuses with a script.
   Two of the worst findings were counts that looked right: a release plan claiming "all 25
   MUST requirements" when there were 28, and a coverage table that appeared complete.
2. **Compare in both directions.** A→B finds missing entries; B→A finds *invented* ones. Both
   matter, and the second is the more damaging.
3. **Verify the claim a document makes about itself.** If a header says "set programmatically
   from the coverage table", check it against the coverage table - ours deviated in four rows.
4. **Follow every ID reference.** A citation like "(REQ-005)" next to the word *category* is
   wrong when categories are REQ-008; nothing but reading the reference catches it.

Useful shape, adapt as needed:

```bash
# priorities, mechanically
grep -oE '^\| (REQ-[0-9]+) \|.*\| (MUST|SHOULD|COULD)[^|]*\|$' requirements.md

# both directions between two documents
comm -23 setA.txt setB.txt   # in A, missing from B
comm -13 setA.txt setB.txt   # in B, not in A

# does the concept actually mention what the table claims it covers?
for r in REQ-052 REQ-058 REQ-081; do echo "$r: $(grep -c "$r" concept.md)"; done
```

**The graph as the extraction layer (2026-09-12, CHG-135):** `graph.json`
(generated by build_index.py) plus `tools/query_graph.py` mechanize steps 1, 2
and 4 for the register graph: `neighbors <ID>` (all edges, both directions),
`impact <ID>` (transitive dependents to re-check), `uncovered --type <T>`
(nodes missing an edge type - the "missing" failure mode as one command),
`path <A> <B>`. The build validator already warns on edges to nonexistent IDs.
The four failure modes stay the question; the graph is the fastest way to
answer them across documents.

That last one found the sharpest defect of the whole review: three requirements whose only
occurrence in the concept was the table row asserting they were covered.

## The four failure modes

| Mode | What it looks like | How it is found |
|---|---|---|
| **Missing entry** | B lacks something A has | A→B comparison |
| **False entry** | B asserts coverage that does not exist | B→A comparison, then grep the target for the ID |
| **Circular coverage** | The only evidence for a claim is the claim itself - a coverage row pointing at a section that never mentions the item | grep the referenced section for the ID; zero hits |
| **Stale rationale** | "X is excluded because question Y is open" - long after Y was answered | when closing a question, grep its ID across the repo |

Circular coverage is the one to watch for after a review: a finding says "item Z is missing
from the table", the table gets a row, and the *content* is never written. The finding closes,
the gap remains, and now it is documented as covered.

## Drift pairs in a spec-driven repo

Check these against each other, both directions:

- requirements ↔ coverage table in the phase output
- coverage table ↔ traceability matrix
- requirements ↔ release plan (membership *and* priority)
- decisions ↔ the documents that cite them
- open-question register ↔ everything that references a question ID
- glossary ↔ terms actually used

### Two couplings that break quietly

**Legend coupling.** If the priority legend says `MUST = MVP`, then a MUST that is not in the
MVP release is a contradiction in the legend, not just a scheduling detail. Either annotate the
priority (`MUST (when X opens)`) or move the item. We hit this exactly once and it took a
scope decision to resolve.

**Scope coupling.** A document headed "coverage (MVP scope)" and a release plan listing "not in
R1" must contain the same set. When they differ, one of them is lying to the reader about what
is being built.

**Stale-item check (2026-10-08, with the backlog register):** if the
project has a `BACKLOG.md` (BKL-###), sweep it too: (a) any row whose
status is NOT open/in-progress/blocked = the row should have been
deleted at close (report, never delete yourself - the registrar owns
that); (b) any open row with neither a Links ID nor a named owner =
drift finding; (c) BKL items also covered by an open OQ/FR = duplication
finding against the register's non-duplication rule.

**Artifact-freshness check (2026-10-14, after the phase documents
fossilized in a real project - concept docs untouched for months while
dozens of changes shipped, and gross UI defects lived in behaviour no
artifact defined):** sweep the LIVING artifact set against reality,
mechanically:

- (a) Per living artifact: `git log -1 --format=%ad -- <path>` vs the
  number of CHGs since that date whose `affects` edges touch its IDs
  (`query_graph.py impact <ID>`). Drift beyond the project threshold
  (default: >10 CHGs) = staleness finding.
- (b) `python tools/query_graph.py uncovered --type behaviour` -
  observable behaviour (BEH-###) WITHOUT a `Verified by` test link is
  the "button with no effect" class; every uncovered row is a finding.
- (c) `uncovered --type section` - concept sections no living REQ
  references anymore = potentially obsolete prose; report, do not
  delete (freezing a baseline is an owner decision, recorded with a
  banner in the doc).
- (d) Frozen documents carrying no frozen-banner = finding (a doc that
  looks alive but is not is worse than an honestly frozen one).

The two-tier rule behind this: TIER-1 artifacts (STATE, BACKLOG,
CHANGELOG, DECISIONS, requirements, IF/SUB registers, TC allocation +
test suites, BEHAVIOUR.md, RELEASES/ROADMAP, generated INDEX/
TRACEABILITY/graph) must be current at all times; TIER-2 phase
documents (02-solution-concept, 03-validation-concept, 04-architecture
prose, gate records) are deliberately FROZEN baselines once the project
enters incremental mode - marked with a banner so no agent cites them
as current truth.

## Multi-agent editing rule

Learned the expensive way: two agents fixed the same review finding in the same file, and the
concept ended up carrying **both paragraphs, committed**.

> **The holder of the file edits it. The reviewer reports and does not patch.**

If you are reviewing, write findings with locations and suggested fixes, and stop there. If you
have already started editing when you learn someone else holds the file, say so immediately and
name the exact paragraphs you inserted - a duplicate is far cheaper to remove while someone
still remembers it exists.

## Artifact dates

A lighter failure mode seen in practice: a session that ran across several days produced
artifacts all dated with the session's start day. The durable log then appears to have a
gap. Date artifacts with the **calendar day they are written**; if a session crosses a date
boundary, say so in the durable log rather than back-dating or leaving the gap.

## Checklist

- [ ] Every count in the documents reproduced mechanically?
- [ ] Each drift pair compared in **both** directions?
- [ ] Every "covered by section X" verified by grepping X for the ID?
- [ ] Self-descriptions ("set programmatically from Y") verified against Y?
- [ ] Every recently closed question's ID grepped for stale rationales?
- [ ] Priority legend consistent with release membership?
- [ ] Same-scope documents holding the same set?
- [ ] Artifact dates matching the calendar days they were written (or the crossing noted)?
- [ ] Only one agent editing each file?
- [ ] Artifact-freshness: living artifacts within the CHG-drift threshold?
- [ ] Every BEH-### row carrying a `Verified by` test link?
- [ ] Frozen documents carrying their frozen-banner (and nothing frozen
  without one)?
