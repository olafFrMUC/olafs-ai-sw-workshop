# Skill: additive contract evolution (the DEC-023 pattern)

How to extend a shipped interface contract **without a breaking change** -
a new optional field, a new `reason` code, a new response shape - so old
consumers keep working untouched. Distilled from three recurrences in
geo-knowledge-guide within two weeks (2026-08/09): the `marker_positions`
seam (IF-007 per-item geo, DEC-023), the `item_facts` additive field
(R1-minimal answer synthesis), and the `time_mode` field plus the
IF-002 candidate seam (`ids_only` / fact-window pushdown).

**Use when:** a shipped `IF-###` contract needs new observable behavior and
the question is "extend or break?"; a producer must expose data the current
envelope does not carry; a caller only needs part of a payload and you are
tempted to widen the default response.

---

## 1. The one rule

**Additive-only within a minor version. Never a breaking change.** Every
contract module in `src/contracts/` states it in its docstring (IF-007:
"Additive-only within a minor version (new optional fields, new `reason`
codes). Consumers must switch on `status` defensively."). The discipline
that makes it safe is mechanical: an additive extension is an **optional
field with absent/default semantics**, never a required one.

The test for "is this additive?": an old consumer, given a response that
carries the new field, behaves **exactly** as before (it ignores the
field); an old producer, given a request that omits the new field, behaves
**exactly** as before (the default preserves prior behavior bit-for-bit).
If either half fails, it is a break, not an extension.

## 2. Additive vs. new contract/version - the decision

**Legitimate additive evolution** (do it, no owner version question):

- A new **optional request field** whose default reproduces today's
  behavior (`time_mode: TimeMode = TimeMode.EXISTENCE` - pre-unit-3 default;
  `ids_only` / `response_shape` on `StoreQueryRequest` - the classic
  full-item response stays the default, bit-identical).
- A new **optional response channel** old consumers ignore
  (`marker_positions`, `item_facts` on the IF-007 envelope).
- A new **`reason` / enum value** in a closed vocabulary consumers already
  switch on defensively.
- A new **response shape** selected by an additive option, where the
  *constraint evaluation is unchanged* and only the payload projection
  differs (the 2026-09-13 candidate seam).

**Requires a new contract / major version / owner escalation** (STOP and
propose, do not guess):

- Making an optional field **required**, renaming, or changing a type.
- Changing the **meaning** of an existing field or the default's behavior.
- Anything that forces old consumers to change to keep working.
- Field placement that ripples onto a **shared type** other contracts
  depend on. DEC-023 rejected a per-item geo field on `StoredItem`
  precisely because it ripples the shared IF-002/IF-001 type onto the write
  path - the additive alternative (an envelope-level optional map keyed by
  `StoredItem.id`) leaves the shared type untouched.
- The marker-seam handoff states the escalation rule verbatim: "If stage 0
  finds the seam cannot be kept additive (a versioning break), STOP and
  escalate to the owner with options - that would change the decision's
  premise."

## 3. The mechanics that make it safe

**Absent/default semantics.** The new field is `| None = None` (or an enum
with the pre-change value as default). "Absent" and "explicit null" are
distinct, documented meanings where it matters: DEC-023 - an id *absent*
from `marker_positions` means "position unknown to this response", an
explicit `null` means "matched but placeless". Malformed input counts as
absent. **Never fabricate** values to fill the channel (positions are never
invented; facts are never generated or paraphrased).

**Schema pins.** The Pydantic module in `src/contracts/` is the single
source of truth; the checked-in JSON Schemas under `src/contracts/schemas/`
are regenerated from it (DEC-021). The contract JSON and the types change
together or not at all.

**Drift guards on both sides.** Frontend `src/types.generated.ts` is
*generated* from the checked-in IF-007 JSON schemas by
`frontend/scripts/gen-if007-types.mjs`; `frontend/tests/schema-drift.test.ts`
mechanically asserts the checked-in file equals what the schemas generate.
Codegen, not a comparison check - TypeScript types vanish at runtime, so a
comparison guard could only diff a second hand-maintained copy (the drift
it should prevent). The backend additionally validates its own responses
against the same schema files at the HTTP boundary (`app.py` `_respond`), so
a scripted envelope that compiles against `types.generated` is a shape the
real backend can emit. DEC-023 consequence, recorded: "Schema JSON
regenerated (DEC-021 drift guard), `types.generated.ts` regenerated by
codegen."

**Bit-identical default, tested.** The candidate-seam handoff makes the
strongest form explicit: "Semantics of the RESULT must be bit-identical
(same items, same order, same matched_via, same facts surfaced) - only the
payload path changes", and the tests assert "the bit-identical-result
property against the classic path on a fixture". When the additive option
is a *projection* (ids-only, facts-only), assert the returned set equals
exactly what the classic path would have produced for the same constraint.

**Registrar steps.** An additive extension is still a contract change and
is registered as one: a DEC record (DEC-023 for `marker_positions`), a CHG
entry, and the register-currency close (STATE, INDEX, handoff marked done).
The unit writes the DEC itself - "the unit writes it - next free DEC
number" - and it records not just the field but the *placement decision and
the rejected alternatives* (DEC-023 documents why envelope-level over a
per-item field, why the data-path order, and the explicitly-accepted
load-bearing risk).

## 4. The sequencing

Contract first, then producer, then consumer - and a scope gate before any
of it:

1. **Stage 0 - scoping memo (before any code).** Write down the exact
   additive extension: field name, shape per item, nullability, versioning
   note - "minimal, per the criteria's needs". This is the unit's built-in
   scope gate; it is where you discover whether the seam can stay additive
   at all. The marker-seam handoff gates stage 1 on it.
2. **Contract + producer.** Extend the contract module additively,
   implement the producer, contract tests green; regenerate schema JSON and
   the frontend types. Record the DEC.
3. **Consumer.** The consumer reads the new optional channel defensively;
   absent channel = the pre-change behavior.
4. **Re-pin / measurement.** If the change discharges a deferral, re-run
   the relevant measurement and re-pin honestly (the marker half was
   re-measured on the box after the seam was wired; harness plumbing only,
   no criteria changes).

For the *producer* of a projection seam there is a measured discipline
behind "let the caller declare what it actually consumes": the 2026-09-12
root-cause record proved that fetching full payloads for a caller that only
needs ids has a ~7-8 s physics floor (312 MB JSONB for ~14k items) that no
semantics-bit-identical change can bring under the cap. The additive
`ids_only` / facts-projection options exist because the narrow scan was
already fast (0.65 s) - the seam lets the caller skip work it would
discard. **Measure the floor before choosing the seam shape** (that record
falsified three candidate hypotheses with numbers before proposing A+B).

## 5. Failure modes observed

- **Widening the shared type instead of adding an envelope channel.** The
  per-item field on `StoredItem` was rejected because it ripples IF-002/
  IF-001 onto the write path - additive at the envelope, keyed by id, keeps
  the shared contract and the write path untouched. Evidence: DEC-023
  options (a)-(B).
- **A default that is not bit-identical.** If the "classic" path changes
  behavior when the new field is absent, old consumers break silently. The
  candidate-seam tests exist to catch exactly this.
- **Fabricating values to populate the channel.** Null honesty is part of
  the contract: items without geo get an explicit null, never an invented
  position; frontend renders no marker for null/absent (never 0,0).
- **Hand-maintaining the TS types (or a second copy to "compare").** That
  is the drift the guard exists to prevent. Codegen from the checked-in
  schemas; the drift-guard test fails the moment they diverge. Never edit
  `types.generated.ts` by hand.
- **Skipping the DEC because "it is only additive".** Additive is still a
  contract change; the register entry (DEC + CHG) is what lets a later
  session learn the placement rationale and the accepted risk without
  re-deriving it. The marker-seam DEC records a *load-bearing convention*
  (`content.geo` read at the IF-007 boundary) as an explicitly accepted
  risk with a named migration path - that honesty is only durable because
  it is in the DEC.
- **Guessing the seam shape before measuring.** The store-leg unit's
  candidate hypothesis (unindexed time-window scan) was falsified by a 106
  ms EXPLAIN ANALYZE; the real cost was payload materialization elsewhere.
  Measure first, then scope the additive seam to the measured floor.
- **Letting a review pin go stale silently.** When an additive decision
  deliberately reverses an existing expectation (the A-4 taxonomy pin), the
  record flags it report-first - "the pin needs an update in the closure
  unit, not the mapping" - rather than letting a red test masquerade as a
  regression.

## 6. Quick checklist for the next additive extension

- [ ] Stage-0 memo: field name, shape, nullability, versioning note -
      confirmed additive (old consumer + old producer both unchanged)
- [ ] Optional field with absent/default semantics; never required;
      malformed/absent distinguished from explicit null where it matters
- [ ] No ripple onto a shared cross-contract type (envelope-level keyed by
      id if a per-item field would ripple)
- [ ] Producer implemented; schema JSON regenerated; frontend
      `types.generated.ts` regenerated by codegen; drift-guard test green
- [ ] Bit-identical default asserted against the classic path on a fixture
- [ ] Never-fabricate rule stated and honored (explicit null, not invented)
- [ ] DEC recorded (placement + rejected alternatives + accepted risks),
      CHG entry, register currency
- [ ] If it discharges a deferral: measurement re-run, harness plumbing
      only, no criteria change
